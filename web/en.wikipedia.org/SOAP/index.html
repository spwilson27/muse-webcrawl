SOAP (formerly an acronym for Simple Object Access Protocol) is a messaging protocol specification for exchanging structured information in the implementation of web services in computer networks. It uses XML as its message format and relies on other application layer protocols, most notably HTTP, for message negotiation and transmission.

SOAP allows developers to invoke processes running on disparate operating systems (such as Windows, macOS and Linux) to authenticate, authorise and communicate using XML. Because web protocols such as HTTP are installed and running on all operating systems, SOAP made it possible for clients and servers to communicate even across firewalls and differing environments.

History

SOAP grew out of work by Dave Winer, Don Box, Bob Atkinson and Mohsen Al-Ghosein at Microsoft in 1998, building on the earlier XML-RPC. It was submitted to the IETF in 1999 and published as SOAP 1.1 in May 2000. The specification was taken over by the World Wide Web Consortium, which published SOAP 1.2 as a Recommendation in 2003 (second edition 2007). From version 1.2 onwards, the letters were officially no longer treated as an acronym, because the protocol is neither simple nor limited to object access.

Message structure

A SOAP message is an ordinary XML document containing an Envelope element that identifies the document as a SOAP message. Inside the envelope sit an optional Header, which carries application-specific information such as authentication credentials, and a mandatory Body, which contains the actual call and response data. A Fault element within the body reports errors. SOAP messages are commonly carried over HTTP POST requests.

Related specifications

SOAP services are typically described using the Web Services Description Language (WSDL), which defines endpoints and operations in machine-readable form. A family of additional specifications, collectively branded "WS-*", layers further features on top of SOAP: WS-Security for message-level security, WS-Addressing for routing, WS-ReliableMessaging for guaranteed delivery, and WS-AtomicTransaction for distributed transactions.

Comparison with REST

From the mid-2000s, the simpler architectural style known as REST, usually exchanging JSON rather than XML, displaced SOAP in most new public web APIs because of its lighter weight. SOAP nevertheless remains widespread in enterprise, banking, telecommunications and government systems, where its strict contracts, formal typing and standardised security features are valued.

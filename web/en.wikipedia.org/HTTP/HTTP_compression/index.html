HTTP compression

HTTP compression is a capability that can be built into web servers and web clients to reduce the amount of data that needs to be transferred, improving bandwidth usage and page-load speed. Data is compressed before it is sent from the server; a compliant client announces which compression schemes it supports in the Accept-Encoding request header, and the server replies with the Content-Encoding header identifying the scheme applied.

Compression schemes

  • gzip — the most widely used scheme for many years, based on the DEFLATE algorithm (LZ77 plus Huffman coding).
  • deflate — the raw zlib/DEFLATE format; historically implemented inconsistently by some clients.
  • Brotli (br) — developed by Google, standardised in RFC 7932; with a built-in dictionary of common web content, it usually compresses text better than gzip and is now supported by all major browsers, generally over HTTPS only.
  • Zstandard (zstd, RFC 8878) — a fast modern algorithm added to browsers and servers in the mid-2020s.
  • compress (LZW) and identity (no compression) are defined but rarely used.

Negotiation and proxies

Clients send an Accept-Encoding header listing supported schemes, optionally with quality values. Servers select the best mutually supported scheme and mark the response with Content-Encoding and a Vary: Accept-Encoding header so caches store variants correctly. Compression is typically applied to text-based formats (HTML, CSS, JavaScript, JSON, XML) and skipped for already-compressed media such as JPEG, PNG, and most video.

Security considerations

Compression combined with encryption has enabled side-channel attacks such as CRIME and BREACH, in which an attacker who can inject chosen text and observe ciphertext sizes infers secrets. Mitigations include disabling compression for sensitive responses, separating secrets from user input, and adding random padding. Header compression in HTTP/2 (HPACK) and HTTP/3 (QPACK) is a separate mechanism targeting header fields rather than message bodies.

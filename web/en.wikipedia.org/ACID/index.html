ACID

ACID is an acronym for the four properties that guarantee reliable processing of database transactions: atomicity, consistency, isolation, and durability. The concepts were formulated in the 1970s by Jim Gray and others; the acronym itself was coined by Andreas Reuter and Theo Härder in 1983.

The four properties

Atomicity requires that a transaction be all-or-nothing: if any part fails, the whole transaction is rolled back as though it never occurred. Consistency means a transaction takes the database from one valid state to another, preserving all defined rules and constraints. Isolation ensures that concurrently executing transactions do not interfere, so the result is as if they ran serially; databases implement this through locking or multiversion concurrency control, with several standard isolation levels trading strictness for performance. Durability guarantees that once a transaction commits, its effects survive crashes, typically via write-ahead logging to persistent storage.

ACID and distributed systems

Strict ACID is straightforward on a single machine but costly across distributed databases, where the CAP theorem forces trade-offs under network partitions. Many large-scale systems adopt the weaker BASE model (basically available, soft state, eventually consistent), while techniques such as two-phase commit, consensus protocols, and NewSQL architectures attempt to deliver ACID semantics at scale.

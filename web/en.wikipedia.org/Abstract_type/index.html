Abstract type

In programming languages, an abstract type (also called an abstract data type, or ADT) is a type whose behavior is defined by a set of operations and values, without specifying how those operations are implemented or how the values are represented in memory. Clients of an abstract type interact with it only through its declared interface, so the implementation can be changed without affecting client code. The concept is central to information hiding, modularity, and object-oriented and functional programming.

Definition

An abstract type is specified by the operations that can be performed on its values, the axioms or contracts those operations must satisfy, and the errors they may signal. A stack, for example, is defined by push, pop, top and isEmpty operations obeying the rule that popping a stack reverses the effect of the most recent push. Whether the stack is stored in an array or a linked list is invisible to clients.

History

The idea was articulated in the 1970s by Barbara Liskov and Stephen Zilles, who introduced abstract data types in the language CLU, and by John Guttag, whose work on algebraic specification gave ADTs a formal foundation. Liskov later received the Turing Award in part for contributions to data abstraction.

Implementations

Languages support abstract types in various ways: abstract classes and interfaces in Java and C#, type classes in Haskell, modules with opaque types in ML and OCaml, and traits in Rust. In each case, the type system prevents client code from depending on the hidden representation, a property sometimes called representation independence.

Benefits and limitations

Abstract types improve maintainability and reasoning: invariants can be enforced at the boundary of the type, and implementations can be optimized or replaced freely. The main cost is the loss of some optimization opportunities that require knowledge of the representation, and the design effort needed to choose a complete yet minimal interface.

Distributed transaction

Field: Database systems, distributed computing

Property guaranteed: ACID across multiple resources

Key protocol: Two-phase commit (2PC)

Standard: X/Open XA

A distributed transaction is a database transaction in which two or more network hosts, databases, or other transactional resources participate. It extends the guarantees of an ordinary transaction — atomicity, consistency, isolation, and durability (ACID) — across the participating resources, so that the entire set of operations either commits or rolls back as a single unit, even in the presence of failures.

Two-phase commit

The classic protocol for coordinating a distributed transaction is two-phase commit (2PC). A transaction coordinator asks every participant to prepare — that is, to promise that it can commit — and records their votes. If all participants vote yes, the coordinator instructs them all to commit; if any votes no, all are told to abort. The protocol guarantees atomicity but can block if the coordinator fails after participants have prepared.

Standards and implementations

The X/Open XA standard defines the interface between a transaction manager and resource managers such as relational databases and message queues, enabling a single transaction to span, for example, an Oracle database and an IBM MQ queue. Application servers and transaction monitors have long provided XA support, and the Java Transaction API (JTA) exposes it to enterprise applications.

Challenges and alternatives

Distributed transactions can hurt scalability and availability, since participants hold locks while coordination proceeds. In microservice architectures, alternatives such as the saga pattern — a sequence of local transactions with compensating actions — and eventual consistency are often preferred. The CAP theorem formalizes the trade-offs involved in maintaining consistency across a network that can be partitioned.

Thrashing (computer science)

From Wikipedia, the free encyclopedia

Thrashing
FieldOperating systems, virtual memory
CauseWorking sets of active processes exceed available physical memory
SymptomsExcessive paging, high disk activity, low CPU utilisation

In computer science, thrashing is a state in which a computer's resources are consumed by the process of swapping data in and out of memory rather than by executing applications. It typically occurs in virtual memory systems when the combined working sets of the running processes exceed the amount of available physical memory (RAM), so the system spends most of its time servicing page faults.

Mechanism

Modern operating systems move pages between RAM and a backing store such as a hard disk or SSD. If processes are continually forced to evict pages that they will need again almost immediately, the page fault rate rises sharply: the disk queue saturates, CPU utilisation paradoxically falls because processes are blocked waiting for pages, and a naive scheduler may respond by admitting still more processes, worsening the problem. The classic analysis is associated with Peter Denning's working set model (1968), which showed that each process needs its current working set of pages resident to run efficiently.

Causes and remedies

Thrashing can result from running too many memory-hungry programs at once, from poor locality of reference in application code, or from global page-replacement policies that let one process steal frames from all others. Remedies include adding physical memory, reducing the degree of multiprogramming, using working-set or page-fault-frequency replacement strategies, swapping out entire processes, and, on personal computers, simply closing applications. Solid-state drives mitigate the penalty of paging but do not remove the underlying imbalance.

Other contexts

The term is also used for analogous behaviour in other resource systems: cache thrashing, when competing data repeatedly evicts useful entries from a CPU cache, and thrashing in databases or TLBs. In each case a shared fast resource is over-committed so that overhead dominates useful work.

Test-driven development

The test-driven development cycle: write a failing test, make it pass, then refactor.

Test-driven development (TDD) is a software development process that relies on the repetition of a very short development cycle: first the developer writes an (initially failing) automated test case that defines a desired improvement or new function, then produces the minimum amount of code to pass that test, and finally refactors the new code to acceptable standards. Kent Beck, who is credited with having developed or "rediscovered" the technique, stated in 2003 that TDD encourages simple designs and inspires confidence.

Test-driven development is related to the test-first programming concepts of extreme programming, begun in 1999, but more recently has created more general interest in its own right. It is a core practice of agile software development and is closely associated with unit testing, though tests in TDD may be written at several levels of granularity.

The TDD cycle

The process is commonly described as a three-phase cycle, often called red, green, refactor:

  1. Add a test (red). The developer writes a test for a small piece of functionality. Because the functionality does not yet exist, the test fails — it "goes red."
  2. Make the test pass (green). The developer writes the simplest possible production code that makes the test pass, without concern for elegance.
  3. Refactor. With all tests passing, the developer cleans up both the production code and the tests, removing duplication and improving structure, while keeping the tests green.

The cycle is repeated continuously, so that the software grows in small, verified increments. Advocates argue that keeping each step small makes debugging easier: when a test fails, the most recent change is the most likely culprit.

History

Although TDD became widely known through extreme programming in the late 1990s, test-first approaches have older roots. Programmers working on early systems in the 1950s and 1960s sometimes wrote expected outputs before writing code, and the practice appeared in various forms in NASA and industrial projects. Kent Beck popularised the modern form in his book Test-Driven Development: By Example (2002), and it was subsequently taken up by the wider agile community. Frameworks such as JUnit, and its ports to other languages (NUnit, PyUnit, RSpec and many others), made automated unit testing inexpensive and routine.

Benefits and limitations

Studies and practitioner reports commonly cite several benefits: a comprehensive regression test suite grows along with the code; defects are caught close to the moment they are introduced; the discipline of writing tests first tends to produce loosely coupled, modular designs; and the tests serve as executable documentation of the intended behaviour. Programmers also report that the cycle provides a sense of progress and reduces fear of changing code.

Criticism of TDD includes the time required to write and maintain tests, the difficulty of applying it to user interfaces, databases, and code that interacts extensively with external systems, and the risk that developers focus on passing tests rather than on design quality. TDD can also give a false sense of security if tests are poorly designed or if important behaviours are never tested.

Related practices

Several related techniques have evolved from or alongside TDD:

  • Acceptance test–driven development (ATDD) — tests are written at the level of user-visible acceptance criteria, often in collaboration with customers.
  • Behaviour-driven development (BDD) — extends TDD by using a shared, natural-language vocabulary to describe behaviour, implemented in tools such as Cucumber and SpecFlow.
  • Test-first development — the broader principle of writing tests before code, without necessarily following the full red–green–refactor cycle.
  • Continuous integration — the automated suite produced by TDD is typically run on every commit, catching integration problems early.

Software design pattern

Design patterns describe reusable solutions to recurring design problems.

In software engineering, a software design pattern is a general, reusable solution to a commonly occurring problem within a given context in software design. It is not a finished design that can be transformed directly into code; rather, it is a description or template for how to solve a problem that can be used in many different situations. Design patterns are formalised best practices that a programmer can use to solve common problems when designing an application or system.

Object-oriented design patterns typically show relationships and interactions between classes or objects, without specifying the final application classes involved. Patterns that imply mutable state may be unsuited to functional programming languages, and some patterns become unnecessary or are expressed very differently in languages with first-class support for the underlying concepts.

History

The concept of patterns originated in architecture with the work of Christopher Alexander, whose A Pattern Language (1977) described design solutions for buildings and towns. Kent Beck and Ward Cunningham brought the idea to software in 1987. The field took off with the 1994 book Design Patterns: Elements of Reusable Object-Oriented Software by Erich Gamma, Richard Helm, Ralph Johnson, and John Vlissides — known as the "Gang of Four" (GoF) — which catalogued 23 patterns and became one of the most influential books in software engineering. Conferences and the pattern community's Pattern Languages of Programs (PLoP) gatherings continued to document patterns in many domains.

Classification

The Gang of Four divided their patterns into three families:

  • Creational patterns concern object creation mechanisms: Abstract Factory, Builder, Factory Method, Prototype, and Singleton.
  • Structural patterns concern how classes and objects are composed: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, and Proxy.
  • Behavioural patterns concern communication between objects: Chain of Responsibility, Command, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, and Visitor.

Other catalogues describe architectural patterns that structure whole systems — such as Layers, Pipes and Filters, Broker, and Model–View–Controller (MVC) — as well as concurrency patterns, enterprise application patterns, and domain-specific collections.

Structure of a pattern description

A pattern description typically includes the pattern's name (which becomes part of a shared design vocabulary), the problem it addresses, the context and forces at play, the solution in terms of elements and their collaborations, the consequences of applying it, and known uses. The name is often considered the most valuable part: terms like "Observer" or "Facade" let designers communicate a whole structure in a word.

Criticism

Design patterns have been criticised on several grounds. Some argue that patterns are workarounds for missing language features — Peter Norvig observed that 16 of the 23 GoF patterns become invisible or simpler in Lisp or Dylan. Patterns can also be over-applied, producing over-engineered designs ("pattern fever"), and novices may force solutions where a simpler design would do. Relatedly, anti-patterns document commonly reinvented bad solutions to problems. Nevertheless, patterns remain a core part of software engineering education and a lingua franca for discussing design.

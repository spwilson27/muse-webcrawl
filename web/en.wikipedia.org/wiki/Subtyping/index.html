Subtyping

In programming language theory, subtyping (also called subtype polymorphism) is a form of type polymorphism. A subtype is a datatype that is related to another datatype (the supertype) by some notion of substitutability: a program element written for the supertype can be used with a value of the subtype in its place. Formally, if S is a subtype of T, written S <: T, then any term of type S can be safely used in any context where a term of type T is expected (Liskov substitution principle).

Origins

The notion of subtyping in programming languages dates back to the 1960s; it was introduced in Simula derivatives. The first formal treatments were developed by John C. Reynolds and later by Luca Cardelli in the 1980s, who systematised the subsumption rule and record subtyping. Barbara Liskov's 1987 keynote and her 1994 paper with Jeannette Wing gave the behavioural characterization — the Liskov substitution principle — widely used in object-oriented design.

Subsumption and coercion

If a value of type S can be used wherever a value of type T is expected, two implementation strategies exist. Under subsumption, the value is used directly, as no representation change is needed (e.g. passing an object of a subclass). Under coercion, the value is automatically converted, as when an integer is widened to a floating-point number in many languages. Subtyping is distinct from type conversion and from inheritance: a class may inherit implementation from another without being its behavioural subtype.

Variance

For composite types such as functions and containers, subtyping depends on variance:

  • Covariant — the subtyping relation is preserved: if A <: B then List[A] <: List[B].
  • Contravariant — the relation is reversed.
  • Invariant — no relation holds between the composite types.

Function types are contravariant in their parameter types and covariant in their return type. Soundness questions around variance are famous: mutable arrays treated covariantly are unsound, which is why Java arrays (covariant) require run-time checks and throw ArrayStoreException, while Java generics are invariant.

Structural and nominal subtyping

In nominal subtyping, relations are declared explicitly (e.g. a class extends another) as in Java, C++ and C#. In structural subtyping, a type is a subtype if it provides all required components with compatible types, as in Go interfaces, OCaml objects and TypeScript. Width subtyping of records (a record with more fields is a subtype of one with fewer) and depth subtyping (fields themselves being subtypes) are basic structural rules.

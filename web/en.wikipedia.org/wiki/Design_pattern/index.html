Software design pattern

In software engineering, a software design pattern is a general, reusable solution to a commonly occurring problem within a given context in software design. It is not a finished design that can be transformed directly into code; rather, it is a description or template for how to solve a problem that can be adapted to many different situations. Design patterns provide a shared vocabulary for developers and capture design experience in a form that can be studied and reused.

History

The idea was borrowed from architecture, where Christopher Alexander developed the concept of a pattern language in the 1970s. In software, the concept was popularised by the 1994 book Design Patterns: Elements of Reusable Object-Oriented Software by Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides — the so-called "Gang of Four" (GoF). The book catalogued 23 patterns for object-oriented design, and pattern-oriented literature has grown extensively since, covering architectural patterns, concurrency patterns, enterprise integration patterns and more.

Classification

The GoF catalogue divides patterns into three families:

  • Creational patterns concern object creation: abstract factory, builder, factory method, prototype and singleton.
  • Structural patterns concern the composition of classes and objects: adapter, bridge, composite, decorator, facade, flyweight and proxy.
  • Behavioural patterns concern communication between objects: chain of responsibility, command, interpreter, iterator, mediator, memento, observer, state, strategy, template method and visitor.

Criticism

Design patterns have been criticised on several grounds: that their overuse can complicate code, that some patterns merely compensate for features missing from a programming language (a critique associated with Peter Norvig's observation that many GoF patterns become simpler or invisible in more expressive languages), and that pattern names are sometimes applied loosely, diluting their meaning. Nevertheless they remain a standard part of software engineering education and practice.

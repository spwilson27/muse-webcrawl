Consistency (database systems)

In database systems, consistency (or correctness) refers to the requirement that a database transaction must change affected data only in valid ways — that is, any data written to the database must conform to all defined rules, including constraints, cascades, triggers, and any combination thereof. It is one of the four ACID properties of transactions, alongside atomicity, isolation, and durability.

ACID consistency

Consistency in the ACID sense guarantees that a transaction brings the database from one valid state to another: if a transaction would violate a declared constraint — such as a uniqueness rule, a foreign key, or a CHECK condition — it is aborted and rolled back, leaving the database in its prior valid state. Maintaining consistency is a shared responsibility: the database system enforces declared integrity constraints, but the application must define the rules that capture the intended semantics of the data.

Consistency models in distributed systems

The term is also used more broadly for the guarantees a system makes about the visibility of writes, especially in distributed and replicated databases. Models range from strong (linearizable) consistency, in which all clients see the same data at the same time, through sequential and causal consistency, to eventual consistency, in which replicas converge to the same value if writes stop.

The CAP theorem states that a distributed data store can provide at most two of consistency (in the linearizability sense), availability, and partition tolerance; since network partitions are unavoidable, designers must trade consistency against availability. The related BASE philosophy (Basically Available, Soft state, Eventual consistency) describes systems that relax ACID consistency for scalability and availability.

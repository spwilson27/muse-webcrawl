Codd's twelve rules

Codd's twelve rules are a set of thirteen rules (numbered zero to twelve) proposed by Edgar F. Codd, the inventor of the relational model of data, as a yardstick for determining whether a database management system (DBMS) is truly relational. Codd published the rules in two articles in Computerworld magazine in October 1985 ("Is Your DBMS Really Relational?" and "Does Your DBMS Run By the Rules?"), after becoming concerned that vendors were marketing products as "relational" when they satisfied only a fraction of his model. Few commercial systems, then or now, satisfy all thirteen rules completely.

The rules

  1. Rule 0 — The foundation rule: A system that is advertised as, or claimed to be, a relational database management system must be able to manage databases entirely through its relational capabilities.
  2. Rule 1 — The information rule: All information in a relational database is represented explicitly at the logical level in exactly one way — by values in tables.
  3. Rule 2 — The guaranteed access rule: Each and every datum (atomic value) in a relational database is guaranteed to be logically accessible by resorting to a combination of table name, primary key value, and column name.
  4. Rule 3 — Systematic treatment of null values: Null values (distinct from the empty character string, a string of blank characters, zero, or any other number) are supported for representing missing information and inapplicable information in a systematic way, independent of data type.
  5. Rule 4 — Dynamic online catalog based on the relational model: The database description is represented at the logical level in the same way as ordinary data, so that authorised users can apply the same relational language to its interrogation as they apply to regular data.
  6. Rule 5 — The comprehensive data sublanguage rule: A relational system may support several languages, but at least one of them must be expressible by a well-defined syntax and support data definition, view definition, data manipulation, integrity constraints, authorisation, and transaction boundaries.
  7. Rule 6 — The view updating rule: All views that are theoretically updatable are also updatable by the system.
  8. Rule 7 — High-level insert, update, and delete: The capability of handling a base relation or a derived relation as a single operand applies not only to retrieval but also to insertion, update, and deletion of data.
  9. Rule 8 — Physical data independence: Application programs and terminal activities remain logically unimpaired whenever changes are made to storage representations or access methods.
  10. Rule 9 — Logical data independence: Application programs remain logically unimpaired when information-preserving changes are made to the base tables.
  11. Rule 10 — Integrity independence: Integrity constraints specific to a particular relational database must be definable in the relational data sublanguage and stored in the catalog, not in application programs.
  12. Rule 11 — Distribution independence: The distribution of portions of a database across various locations must be invisible to users of the system.
  13. Rule 12 — The nonsubversion rule: If a relational system has a low-level (single-record-at-a-time) language, that low level cannot be used to subvert or bypass the integrity rules and constraints expressed in the higher-level relational language.

Reception

The rules became a standard reference point in debates about what "relational" means and are still used to evaluate database products. Codd himself later expanded his requirements in the 1990 book The Relational Model for Database Management: Version 2, proposing hundreds of features. Critics note that full compliance is rare — most SQL systems, for example, depart from the model in their handling of nulls and duplicate rows — and Codd's collaborator Christopher Date observed that the rules are best read as a definition of the relational ideal rather than a practical checklist.

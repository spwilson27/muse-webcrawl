Use after free

Use after free is a class of software vulnerability in which a program continues to use a pointer to memory after that memory has been freed (deallocated). Because the freed memory may be reallocated for a different purpose, writing to or reading from the stale pointer can corrupt data, crash the program, or — in security exploits — allow an attacker to execute arbitrary code. In the Common Weakness Enumeration, use after free is catalogued as CWE-416.

Causes

The classic cause is that multiple pointers (aliases) refer to the same dynamically allocated object; when one owner frees the memory, the other pointers become dangling pointers, and any later dereference of them is a use after free. The error commonly occurs in languages with manual memory management such as C and C++, especially in complex code where the ownership and lifetime of objects are unclear, or in error-handling paths where an object is freed but execution continues.

char *p = malloc(sizeof(char) * 100);
free(p);          /* memory returned to the allocator */
strcpy(p, "text"); /* use after free: p is dangling */

Exploitation

Attackers can exploit use-after-free bugs by arranging for the freed region to be reallocated with data they control, so that subsequent use of the stale pointer operates on attacker-chosen values. In object-oriented code, overwriting a freed object's virtual function table pointer can redirect execution to attacker code. Such vulnerabilities have been found frequently in web browsers and operating system kernels.

Prevention and detection

  • Setting pointers to NULL immediately after freeing, so later use faults predictably rather than corrupting memory.
  • Using smart pointers, ownership models (such as Rust's), or garbage collection to tie memory lifetime to object references.
  • Static analysis and sanitizers such as AddressSanitizer, which detect accesses to freed heap regions at run time.
  • Allocator hardening, such as quarantining freed chunks before reuse.

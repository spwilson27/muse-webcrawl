Continuous integration

In software engineering, continuous integration (CI) is the practice of merging all developers' working copies to a shared mainline several times a day, with each integration verified by an automated build and automated tests to detect problems early. The term originated in extreme programming, where it was one of the original twelve practices.

Practices

Proponents such as Martin Fowler recommend that teams maintain a single source repository, automate the build, make builds self-testing, commit to the mainline every day, build every commit on an integration machine, keep the build fast, test in a clone of the production environment, and fix broken builds immediately. A CI server (such as Jenkins, GitLab CI, GitHub Actions or CircleCI) monitors the repository and runs the build pipeline on each change, reporting failures to the team.

Benefits and relation to other practices

CI reduces integration risk by surfacing conflicts and defects while they are small and cheap to fix, and it keeps the software in a constantly working state. It is a foundation for continuous delivery and continuous deployment, which extend automation to release.

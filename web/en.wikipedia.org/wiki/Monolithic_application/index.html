Monolithic application

In software engineering, a monolithic application is a single, self-contained application in which the user interface, business logic and data access code are combined into one program from a single platform, deployed and run as a single unit. It is the traditional architecture for enterprise software and contrasts with distributed designs such as service-oriented architecture and microservices, in which functionality is split among independently deployable components communicating over a network.

Characteristics

A monolith is developed, tested and deployed as one artefact: a single executable or a single web application archive. Internally it may be well modularised — a "modular monolith" — but all modules share one process and one database. Scaling is done by running multiple copies of the whole application behind a load balancer.

Advantages

  • Simpler development, debugging and deployment for small to medium systems.
  • Straightforward cross-cutting concerns (transactions, logging, security) within one codebase and process.
  • No network latency or partial-failure modes between components; refactoring across modules is easy.

Disadvantages

  • As the codebase grows, complexity and build/deploy times increase, and a fault can bring down the entire application.
  • Scaling is coarse-grained: the whole application must scale even if only one feature is hot.
  • Technology changes are all-or-nothing; large monoliths can impede team autonomy.

Versus microservices

The rise of microservices in the 2010s was largely a reaction to the pains of very large monoliths at web-scale companies. Practitioners such as Martin Fowler nonetheless advise starting with a monolith ("monolith first"), since the boundaries of a system are hard to get right in advance, and extracting services later from a modular monolith is usually cheaper than distributing prematurely.

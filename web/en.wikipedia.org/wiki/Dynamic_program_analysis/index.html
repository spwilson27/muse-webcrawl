Dynamic program analysis

Dynamic program analysis is the act of analysing software by executing programs on a real or virtual processor. For dynamic program analysis to be effective, the target program must be executed with sufficient test inputs to cover a variety of possible behaviours. Dynamic analysis is contrasted with static program analysis, which examines code without running it.

Techniques

  • Profiling — measuring time, memory use, and call frequency, with tools such as gprof and perf.
  • Code coverage — determining which statements, branches, or paths were executed by a test suite (e.g., gcov).
  • Memory error detection — tools such as Valgrind (Memcheck), AddressSanitizer, and Purify detect invalid reads/writes, leaks, and use-after-free errors.
  • Thread error detection — ThreadSanitizer and Helgrind detect data races and deadlocks.
  • Taint analysis — tracking the flow of untrusted data through a running program.
  • Dynamic slicing and execution tracing — recording execution histories for debugging and fault localization.
  • Fuzzing — supplying random or mutated inputs to provoke crashes (e.g., American fuzzy lop, libFuzzer), often combined with coverage guidance.

Implementation methods

Dynamic analysis is implemented through compile-time or binary instrumentation (e.g., LLVM's sanitizers, Pin, DynamoRIO), through interpretation or emulation, through operating-system tracing facilities (ptrace, DTrace, eBPF), or through hardware performance counters. Instrumentation typically trades runtime overhead for detail; sampling profilers reduce overhead at the cost of precision.

Advantages and limitations

Because it observes real executions, dynamic analysis can detect errors that actually occur and avoid many false alarms of static analysis, but it can only report on paths that were executed, so results depend heavily on the quality of test inputs. It is a mainstay of software testing, performance engineering, and security auditing.

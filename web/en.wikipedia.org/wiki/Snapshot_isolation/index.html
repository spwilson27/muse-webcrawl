Snapshot isolation

In databases, and transaction processing (transaction management), snapshot isolation is a guarantee that all reads made in a transaction will see a consistent snapshot of the database (in practice, the values it read as of the start of the transaction), and the transaction itself will successfully commit only if no updates it made conflict with any concurrent updates made since that snapshot.

Description

Snapshot isolation is implemented using multiversion concurrency control (MVCC): each transaction reads from a version of the data committed before it began, so readers never block writers and writers never block readers. When a transaction commits, the system checks whether any other transaction that committed concurrently updated the same rows ("first committer wins"); if so, the later transaction is aborted and must retry.

Properties and anomalies

Snapshot isolation prevents the classic read anomalies of dirty reads, non-repeatable reads and phantom reads. However, it is not equivalent to full serializability: it permits the write skew anomaly, in which two concurrent transactions each read a shared state, make updates that are individually consistent, and together violate a constraint spanning the data both read. An extension called serializable snapshot isolation (SSI), implemented in PostgreSQL since version 9.1, detects dangerous read–write dependency patterns and aborts transactions to guarantee true serializability.

Adoption

Snapshot isolation is provided, under various names, by many database systems, including Oracle ("serializable"), PostgreSQL, Microsoft SQL Server (as an explicit isolation level), MySQL's InnoDB in effect via MVCC for consistent reads, and numerous distributed databases.

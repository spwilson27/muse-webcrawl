Model–view–controller

TypeSoftware architectural pattern
First described1979 (Trygve Reenskaug, Xerox PARC)
ComponentsModel, View, Controller
Used inWeb frameworks, GUI toolkits

Model–view–controller (MVC) is a software architectural pattern commonly used for developing user interfaces that divides the related program logic into three interconnected elements: the model, the view, and the controller. The pattern is intended to separate internal representations of information from the ways information is presented to and accepted by the user, promoting modularity and parallel development.

Components

The model is the central component of the pattern. It captures the application's data, business rules and logic, and notifies its associated views and controllers when its state changes. The view renders the model into a form suitable for interaction, such as a screen display, and can exist in multiple forms for a single model. The controller accepts user input and converts it into commands for the model or view, mediating between the two.

In typical implementations, the view obtains display information from the model, either directly through queries or indirectly when the model pushes change notifications.

History

MVC was introduced by Trygve Reenskaug in 1979 while working on the Smalltalk language at Xerox PARC, originally under the name Thing-Model-View-Editor. It became a core organising principle of the Smalltalk-80 environment and influenced later GUI frameworks.

The pattern found a second life in server-side web development, where frameworks such as Ruby on Rails, Django and ASP.NET MVC apply the separation to HTTP requests, database-backed models and HTML templates.

Variants and criticism

Numerous derivative patterns have been proposed, including Model–view–presenter (MVP), Model–view–viewmodel (MVVM) and hierarchical MVC, each adjusting how the view and the coordinating component interact. Critics note that real applications often blur the boundaries between the components, and that the pattern can add unnecessary complexity to small programs.

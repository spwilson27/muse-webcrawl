Shard (database architecture)

A database shard, or simply a shard, is a horizontal partition of data in a database or search engine. Each shard is an independent database instance held on a separate server, so that the total data set and query load are distributed across many machines. Sharding is the architectural pattern of splitting one logical data set in this way.

How it works

Rows of a table are assigned to shards according to a shard key — for example a customer ID hashed or divided into ranges. A query that supplies the shard key can be routed to the single shard holding the data, while queries spanning all shards must be scattered and gathered. Systems such as Google's Spanner, MongoDB, Elasticsearch and Vitess (for MySQL) implement sharding with varying degrees of automation.

Advantages and disadvantages

Sharding provides horizontal scalability: capacity grows by adding servers rather than by buying a larger machine, and smaller per-shard indexes fit in memory, improving response times. The costs are operational complexity, difficulty of joins and transactions across shards, the need to rebalance data when shards grow unevenly, and reduced availability guarantees for queries that touch every shard. For these reasons sharding is often adopted only when a single-node or read-replica architecture can no longer cope.

The term was popularised in part by its use in massively multiplayer online games, where separate copies of a game world are also called shards.

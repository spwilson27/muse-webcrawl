Atomic transaction

An atomic transaction is an indivisible and irreducible series of database operations such that either all occur, or none occur. A guarantee of atomicity prevents updates to the database from occurring only partially, which can cause greater problems than rejecting the whole series outright. Atomicity is the first of the four ACID properties (atomicity, consistency, isolation, durability) that define correct transaction processing.

Example

Consider transferring money between two bank accounts: the debit from one account and the credit to the other must happen together. If the system fails after the debit but before the credit, the money would vanish from the database's point of view. An atomic transaction guarantees that either both operations are recorded (the transaction commits) or the partial work is undone (the transaction rolls back or aborts), leaving the database as though the transaction had never started.

Implementation

Atomicity is typically implemented using a write-ahead log: before modifying data in place, the system records the intended changes in a durable log. After a crash, the log is replayed to redo committed transactions and to undo those that were in progress. Shadow paging is an alternative technique in which modified pages are written to new locations and made visible by atomically updating a root pointer.

Distributed transactions

When a transaction spans several databases or services, atomicity is harder to achieve. The classic solution is the two-phase commit protocol, in which a coordinator asks all participants to prepare and then either commit or abort unanimously. Because two-phase commit can block if the coordinator fails, many modern distributed systems instead relax strict atomicity in favour of eventual consistency and compensation-based designs such as sagas.

Outside databases

The concept also appears in operating systems and programming languages: atomic operations in concurrent programming, transactional memory, and atomic file-system updates all borrow the same all-or-nothing guarantee, implemented with mechanisms such as compare-and-swap instructions and journaling.

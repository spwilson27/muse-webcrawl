Regression testing

Regression testing (rarely, non-regression testing) is re-running functional and non-functional tests to ensure that previously developed and tested software still performs after a change. If the software fails such a test, it is said to have regressed. Changes that may require regression testing include bug fixes, software enhancements, configuration changes, and even substitution of electronic components.

Regression tests are re-run after each change to catch regressions early

Background

As software is modified, new faults may be introduced or old faults may reappear. A common cause is that a programmer fixing one problem unintentionally breaks behaviour elsewhere in the system. A regression test suite accumulates test cases that have been created for previously found defects and for core functionality, and these are replayed after every significant change.

Practices

Ideally the entire test suite is re-run, but because full regression testing can be expensive in time and computing resources, teams use test-case selection and prioritisation techniques to run the most relevant or highest-risk tests first. Regression suites are strongly associated with test automation and with continuous integration pipelines, where they run automatically on each commit. Techniques such as capture/replay, comparison testing against expected outputs, and smoke tests are commonly used.

A well-known rule of thumb, sometimes called the pesticide paradox (after Beizer), notes that repeatedly running the same tests eventually stops finding new defects, so test suites must also be periodically reviewed and extended.

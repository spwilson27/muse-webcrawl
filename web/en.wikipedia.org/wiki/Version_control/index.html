Version control (also known as revision control, source control, or source code management) is the software engineering practice of controlling, organizing, and tracking different versions in history of computer files, primarily source code text files, but generally any type of file. Version control is a component of software configuration management.

A version control system (VCS) records changes to files over time so that specific versions can be recalled later. It allows multiple developers to work on the same files simultaneously, keeps a complete history of who changed what and why, and makes it possible to revert files or whole projects to earlier states, compare changes across time, and experiment safely on separate lines of development.

History

Early tools managed single files locally: SCCS (Source Code Control System, 1972) and RCS (Revision Control System, 1982) stored successive versions as interleaved deltas. CVS (Concurrent Versions System, 1990) extended RCS to whole directory trees over a network, becoming the dominant open-source system of the 1990s. Subversion (2000) was designed as a modernized CVS with atomic commits, directory versioning, and branching by copying. In 2005, Linus Torvalds created Git for development of the Linux kernel, and distributed systems such as Git and Mercurial became the industry standard; by the 2010s Git, hosted by services such as GitHub, was overwhelmingly dominant.

Models

Centralized

In a centralized model, a single server holds the canonical repository and clients check out working copies, committing changes back to the server. CVS, Subversion, and Perforce follow this model. It offers simple administration and access control but creates a single point of failure and requires network access for most history operations.

Distributed

In a distributed version control system (DVCS), every client mirrors the full repository, including its complete history. Developers commit locally and synchronize with peers by pushing and pulling changes. Git, Mercurial, and Darcs are distributed systems; the model supports offline work, cheap branching, and flexible collaboration topologies.

Core concepts

  • Repository — the database storing files and their complete change history.
  • Working copy — the checked-out files a developer edits.
  • Commit (or revision) — a recorded snapshot of changes, with a message, author, and timestamp; commits form a history graph.
  • Branch — an independent line of development within the repository.
  • Merge — combining changes from different branches; overlapping edits can produce merge conflicts that must be resolved manually.
  • Tag — a named marker attached to a specific revision, typically a release.
  • Diff — a display of the differences between two versions of a file or project.
  • Blame/annotate — showing which author and commit last modified each line of a file.

Beyond source code

The same techniques are applied to documents, configuration files, infrastructure definitions ("infrastructure as code"), datasets, and collaborative writing. Modern wikis and document platforms include simplified built-in revision histories, and content-addressable storage designs borrowed from systems like Git underlie many backup and synchronization tools.

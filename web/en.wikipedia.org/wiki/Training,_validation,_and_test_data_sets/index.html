Training, validation, and test data sets

From Wikipedia, the free encyclopedia

Training, validation, and test data sets are disjoint subsets into which a data sample is partitioned in machine learning, particularly in supervised learning, in order to train a model, tune its hyperparameters, and estimate its performance on unseen data. Keeping the three subsets separate prevents the model from being evaluated on data it has already seen, which would give an optimistic and misleading estimate of how it generalises.

Definitions

A training data set is the subset used to fit the parameters of a model — for example, the weights of a neural network or the coefficients of a linear regression. The model sees and learns from these data during training.

A validation data set (also called a development set or dev set) provides an (approximately) unbiased evaluation of a model fitted on the training data, typically while tuning hyperparameters such as the learning rate, regularisation strength, or network architecture. Many candidate models may be compared on the validation set, and the best is selected.

A test data set (also called a holdout set) is used only once, after training and selection are complete, to estimate the final performance of the chosen model. It should play no role in fitting or in model selection, precisely so that the final estimate is not biased by repeated adaptation to the evaluation data.

Why three sets?

If only a training and a test set are used, and hyperparameters are chosen to maximise test-set performance, the test set has effectively become part of model selection: the reported score no longer reflects performance on genuinely unseen data. This phenomenon is a form of overfitting — the model (or the researcher) adapts to idiosyncrasies of the test data. The three-way split isolates the final evaluation from every design decision.

Typical proportions vary with the amount of data available. A common rule of thumb is 60–70% for training, 10–20% for validation and 10–20% for testing. With very large data sets (millions of examples), fractions as small as 98/1/1 or even 99.5/0.25/0.25 may suffice, since a small fraction still yields a large absolute number of examples.

How the split is performed

The partition should generally be random, so that each subset is representative of the whole. For classification tasks, stratified splitting preserves the class proportions in each subset. For time-series data, random splitting is inappropriate because it leaks future information into the past; instead the data are split chronologically, with the test set taken from the most recent period.

When data are scarce, cross-validation provides a more efficient alternative: the data are repeatedly partitioned into training and validation folds, and the results are averaged. A separate test set can still be held out for a final check.

Common pitfalls

  • Data leakage: information from the validation or test set influencing training, e.g. by performing feature normalisation or feature selection on the full data set before splitting.
  • Duplicate or near-duplicate examples appearing in both training and test sets, inflating measured performance.
  • Test-set reuse: repeatedly evaluating on a benchmark test set (as in public leaderboards) gradually overfits the community's models to it.
  • Distribution shift: the test data coming from a different distribution than the training data, so the split does not measure performance in the deployment environment.

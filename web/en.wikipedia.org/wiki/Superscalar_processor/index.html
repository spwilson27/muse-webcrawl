Superscalar processor

From Wikipedia, the free encyclopedia

Superscalar processor

Architecture class: Instruction-level parallelism

First examples: CDC 6600 (1964), IBM System/360 Model 91 (1967)

Key features: Multiple instruction issue per clock cycle; dynamic scheduling; out-of-order execution

Related: Instruction pipelining, VLIW, Out-of-order execution

A superscalar processor (or superscalar architecture) is a type of central processing unit (CPU) that implements a form of parallelism called instruction-level parallelism within a single processor. In contrast to a scalar processor, which can execute at most one single instruction per clock cycle, a superscalar processor can execute more than one instruction during a clock cycle by simultaneously dispatching multiple instructions to different execution units on the processor chip. Each execution unit is not a separate processor (or a core), but an execution resource within a single CPU, such as an arithmetic logic unit, a bit shifter, or a multiplier.

A superscalar pipeline issues several instructions per cycle to multiple execution units.

Whereas a scalar processor must execute each instruction in a strict sequence, and different instructions can be at different stages of execution at a given time (that is, pipelined), a superscalar processor can be executing several instructions at the same stage of the pipeline at the same time. The superscalar architecture is closely related to the degree of parallelism the compiler and the hardware can extract from ordinary sequential programs: because most modern programs are written as sequences of instructions with data dependencies between them, the hardware must analyze the instruction stream at run time, identify instructions that do not depend on one another, and issue them in parallel. This dynamic discovery of parallelism distinguishes superscalar designs from very long instruction word (VLIW) processors, in which the compiler packages independent operations into wide instructions in advance.

Superscalar designs dominate general-purpose computing: essentially all desktop, laptop, server, and mobile processors introduced since the mid-1990s — including the Intel Core family, AMD Zen processors, and ARM cores such as the Cortex and Apple silicon series — are superscalar, typically issuing between three and ten instructions per cycle.

History

The earliest machine widely regarded as superscalar was the CDC 6600, designed by Seymour Cray and released in 1964. The CDC 6600 used a central processor with ten independent functional units — including separate units for floating-point addition, multiplication, division, and increment operations — coordinated by a mechanism called a scoreboard, which tracked register usage and allowed instructions to be issued to idle units as soon as their operands were available and no conflicts existed. Although the 6600's instruction issue logic was in-order and limited to one instruction per cycle, its ten parallel functional units and scoreboard-based dispatch made it, in effect, the first superscalar design; later analysts such as John H. Crawford and others have classified it as a superscalar machine in the broad sense.

The IBM System/360 Model 91, announced in 1964 and delivered in 1967, introduced Tomasulo's algorithm, a hardware technique for dynamic scheduling using reservation stations and register renaming. Tomasulo's algorithm allows instructions to execute out of order as soon as their operands are ready, while preserving the appearance of sequential execution. Together, scoreboarding and Tomasulo's algorithm form the foundation of virtually all later superscalar scheduling logic.

Through the 1970s and 1980s, superscalar techniques were confined mainly to mainframes, supercomputers, and high-end minicomputers, because they demanded large numbers of transistors. The advent of RISC architectures, whose simple, regular instruction formats made decoding and issuing several instructions per cycle much easier, brought superscalar designs to workstations and personal computers. The Intel i960CA (1989) is often cited as the first commercial superscalar microprocessor; the Pentium (1993) brought dual-issue superscalar execution to the mass-market PC, and the Pentium Pro (1995) combined superscalar issue with out-of-order execution and register renaming in the x86 line. By the late 1990s, superscalar design had become the default organization for high-performance general-purpose processors.

Design

Instruction fetch and decode

A superscalar front end must fetch and decode several instructions per cycle. This places heavy demands on the instruction cache and on branch prediction: a mispredicted branch wastes not only the instructions behind the branch but an entire fetch window several instructions wide. Modern designs therefore employ sophisticated two-level adaptive branch predictors, branch target buffers, and trace caches or micro-operation caches that store already-decoded instructions so that the decode work need not be repeated.

Dispatch, renaming, and scheduling

After decoding, instructions are renamed: architectural registers named by the instructions are mapped onto a larger pool of physical registers, removing false dependencies (write-after-read and write-after-write hazards) that would otherwise serialize execution. Renamed instructions enter reservation stations or an instruction window, where the scheduler continuously checks which instructions have all operands ready and issues them to free execution units. Because the scheduler must compare many instructions against many results each cycle, its complexity grows roughly with the square of the issue width, which is one of the principal practical limits on superscalar width.

Execution units and retirement

A typical superscalar core contains several integer ALUs, one or more floating-point and SIMD units, load and store units connected to the data cache and load-store queue, and branch units. Instructions complete out of order but are retired (committed to the architectural state) in program order using a reorder buffer, so that interrupts and exceptions appear to occur between instructions exactly as in a sequential machine. Speculative results from instructions following an unresolved branch can thus be discarded cleanly if the prediction proves wrong.

Limitations

The achievable parallelism in ordinary programs is limited. Studies of instruction-level parallelism have repeatedly shown that while idealized machines with perfect branch prediction, unlimited windows, and perfect memory disambiguation could in principle sustain very high issue rates, realistic programs — dense with branches, pointer-based memory accesses, and true data dependencies — typically offer only a few independent instructions per cycle on average. Each doubling of issue width yields diminishing returns, while costs in power, die area, verification effort, and scheduling complexity grow steeply.

Memory latency is a second fundamental limit: when an instruction waits on a cache miss, downstream dependent instructions stall, and although large instruction windows can find independent work, they cannot create parallelism that the program does not contain. This is part of the so-called memory wall. Power consumption is a third limit: much of a superscalar core's energy goes not into arithmetic but into fetching, decoding, renaming, scheduling, and moving operands — overhead that grows with width. These constraints motivated the industry's shift, beginning around 2004–2005, toward multi-core processors (thread-level parallelism) and wider vector units (data-level parallelism) as complements to moderate-width superscalar cores.

Alternatives and related architectures

  • Very long instruction word (VLIW) — the compiler, rather than the hardware, finds and bundles parallel operations. This simplifies hardware but requires recompilation for different implementations and struggles with unpredictable latencies such as cache misses.
  • Explicitly parallel instruction computing (EPIC) — exemplified by Intel's Itanium, an attempt to combine compiler-scheduled bundles with hardware support for speculation.
  • Simultaneous multithreading — issues instructions from multiple threads into the same superscalar core, filling issue slots that a single thread leaves empty.
  • Vector processors and GPUs — exploit data parallelism rather than instruction parallelism within a scalar instruction stream.

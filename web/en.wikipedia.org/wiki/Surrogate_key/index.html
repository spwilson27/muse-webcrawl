A surrogate key has no business meaning

A surrogate key (or synthetic key, pseudokey, entity identifier, or factless key) is a unique identifier for either an entity in the modelled world or an object in a database. Unlike a natural key, which is drawn from data that already exists and has meaning in the real world — such as a person's tax identification number or a product's catalogue code — a surrogate key is generated by the system itself and has no intrinsic meaning. It exists solely to identify a row.

Definition and generation

Surrogate keys are typically integers assigned from a sequence or an auto-incrementing column, but they may also be universally unique identifiers (UUIDs/GUIDs), random values, or hash values. The defining properties are that the value is unique, never changes during the life of the row, is never reused, and carries no information that users or applications should interpret. Data warehousing methodology, particularly the dimensional modelling approach popularised by Ralph Kimball, makes heavy use of surrogate keys for dimension tables, where each dimensional row is assigned a fresh surrogate key so that changes in source-system (natural) keys over time can be tracked as new rows — the basis of slowly changing dimension techniques.

Advantages

  • Stability: Natural keys can change (people change names, companies reassign codes); surrogate keys never do, so relationships built on them never break.
  • Performance: A single narrow integer column makes for compact indexes and fast joins, compared with wide or multi-column natural keys.
  • Integration: When data from several source systems is merged, their natural keys may collide; new surrogates sidestep the conflict.
  • Uniformity: Every table follows the same key pattern, simplifying application code and referential integrity management.

Disadvantages and criticism

Critics argue that surrogate keys can mask poor modelling: because uniqueness is enforced artificially, designers must still declare unique constraints on the natural attributes, or duplicate real-world entities can enter the database silently. Surrogates also add an extra lookup when querying by real-world values, and exporting data between systems requires mapping between different sets of surrogates. Some database theorists contend that a well-chosen natural key, where one genuinely exists, is the more honest design.

Surrogate keys versus natural keys

The choice between the two is one of the longest-running debates in database design. In practice, many systems use both: a surrogate key as the primary key used for internal joins and foreign keys, with the natural key retained as a unique alternate key for lookups and business validation.

Directory service

From Wikipedia, the free encyclopedia

A directory organises names and attributes in a hierarchical tree.

A directory service (or name service) is a software system that stores, organises, and provides access to information in a computer system's directory. In software engineering, a directory is a map between names and values, much like a telephone directory, which maps the name of a person to their telephone number and address. Directory services allow network administrators to manage access to information and resources across a network, and they are a central component of network operating systems and identity management infrastructures.

The most widely deployed directory service protocol is the Lightweight Directory Access Protocol (LDAP), which descends from the X.500 directory standards developed for telecommunications networks. Well-known implementations and products include Microsoft's Active Directory, the open-source OpenLDAP, Apple's Open Directory, and the historical Novell eDirectory (formerly Novell Directory Services). Related and predecessor technologies include Sun's Network Information Service (NIS), Banyan VINES StreetTalk, and DNS, which is itself a specialised, globally distributed directory service for host names.

History

The idea of a network directory arose with the growth of computer networks in the 1970s and 1980s. As organisations connected more computers, the need to locate users, printers, file servers, and other resources in a systematic way became pressing. The ARPANET community maintained a central hosts file at the Network Information Center, an approach that did not scale; the Domain Name System (DNS), introduced in the 1980s, solved the analogous problem for host naming by distributing the directory hierarchically.

For general-purpose directory information, the ITU-T and ISO developed the X.500 series of standards beginning in 1988. X.500 specified a comprehensive Directory Access Protocol (DAP), a data model based on entries and attributes, and a global naming scheme. The full X.500 protocol stack, designed to run over the OSI network model, proved heavy for the desktop computers of the early 1990s. Researchers at the University of Michigan therefore developed LDAP, a lighter protocol that ran over TCP/IP and offered most of X.500's functionality; LDAP was first described in RFC 1487 in 1993 and became the dominant access method.

Commercial directory products proliferated in the 1990s. Novell's NetWare Directory Services (later eDirectory) was an early success. Microsoft entered the field with Active Directory in Windows 2000, which combined an LDAP-accessible directory with Kerberos authentication and DNS-based location, and became the standard directory for Windows networks. Sun Microsystems, Netscape, and others marketed directory servers for Internet and enterprise use, and directory technology was absorbed into broader identity and access management platforms.

Concepts

Entries, attributes, and naming

A directory stores information as a collection of entries. Each entry is a set of attributes describing an object such as a person, a group, a printer, or a computer. Every attribute has a type and one or more values; a person's entry might include attributes for common name (cn), surname (sn), telephone number, and email address. Entries are organised into a hierarchical tree called the Directory Information Tree (DIT). Each entry has a unique distinguished name (DN) formed from a naming attribute of the entry itself (its relative distinguished name, RDN) together with the DNs of its ancestors, for example cn=Alice Smith, ou=Engineering, dc=example, dc=com.

Schema

A schema defines the kinds of objects a directory may contain and the attributes each may or must carry. Object classes describe categories of entries: the widely used inetOrgPerson class, for instance, extends the generic person class with attributes suited to Internet-era contact information. Schemas can be extended by administrators, though careless extension complicates interoperability.

Operations

Clients interact with a directory through operations such as search (retrieving entries matching a filter within a subtree), compare, add, delete, modify, and bind, the operation by which a client authenticates itself to the server. Directory workloads are typically read-heavy: searches vastly outnumber updates, and directory implementations are optimised accordingly.

LDAP and X.500

LDAP, currently specified in RFC 4510 and companion documents (version 3), retained the X.500 data model while simplifying the protocol. An LDAP directory can be queried and modified from almost any platform, and LDAP serves as the lingua franca by which applications — mail servers, web applications, VPN gateways, and operating system logons — look up identity information. Active Directory, although it has proprietary extensions, exposes an LDAP interface, as do OpenLDAP, the 389 Directory Server, and Apache Directory Server.

Because LDAP defines only the access protocol and information model, products differ in replication, access control, and management tooling. Standards-adjacent technologies include DSML (an XML representation of directory data) and SPML for provisioning.

Replication and distribution

Directories are usually replicated so that copies of the data exist on multiple servers for availability and performance. Replication models range from single-master (one writable server, many read-only replicas) to multi-master, in which updates may be accepted at several replicas and reconciled, with the risk of conflicts. A large directory may also be partitioned: different subtrees held by different servers, with referrals directing clients from one server to another when a query crosses a partition boundary. Replication is one of the features that distinguishes enterprise directory servers from simple LDAP front ends to databases.

Uses

  • Authentication and single sign-on: verifying user credentials and providing a central account store for many applications.
  • Authorisation: group memberships and attributes in the directory drive access-control decisions.
  • Resource location: finding printers, servers, and shared folders on a network.
  • Address books: email clients query directories for contact information.
  • Public key infrastructure: directories publish certificates and revocation lists.
  • Configuration stores: applications and operating systems keep settings and policies in directory entries.

The rise of cloud computing moved many directory functions into hosted identity providers, which expose directories through web protocols such as SAML, OAuth 2.0, and OpenID Connect, and through the SCIM provisioning standard. Microsoft's cloud directory (Microsoft Entra ID, formerly Azure Active Directory) and services such as Okta follow this model while retaining synchronisation with on-premises LDAP directories in many deployments.

Comparison with relational databases

Directory services differ from general-purpose relational databases in several respects. Directories are optimised for read-mostly workloads and for hierarchical, rather than relational, organisation of data. They offer a standardised network protocol and schema conventions that promote interoperability between vendors, built-in replication, and fine-grained access control on entries and attributes. Conversely, they generally lack transactions spanning multiple entries, joins, and the ad-hoc query flexibility of SQL. For applications centred on identity and lookup, the directory model remains a natural fit; attempts to use directories as general databases, or databases as directories, usually produce poor results.

Two-phase commit protocol

In transaction processing and distributed databases, the two-phase commit protocol (2PC) is a distributed algorithm that coordinates all the processes participating in an atomic transaction so that all either commit or abort it together. It is the classic solution to the atomic commitment problem.

Protocol

One process acts as coordinator; the others are participants (cohorts). In the voting (prepare) phase, the coordinator asks every participant to prepare to commit and to write the transaction durably to its log; each participant replies YES (prepared) or NO. In the decision (commit) phase, if all voted YES the coordinator logs and broadcasts COMMIT; otherwise it broadcasts ABORT. Participants apply the decision, log it, and acknowledge.

Properties and limitations

2PC guarantees atomicity — all-or-nothing — even when individual nodes crash, provided they recover with their logs intact. Its main weakness is that it is a blocking protocol: if the coordinator fails after participants have prepared, the participants must hold locks and wait, unable to resolve the transaction unilaterally. This motivated variants such as three-phase commit (which only partially addresses the problem) and, in modern distributed systems, consensus-based approaches built on Paxos or Raft, and looser models such as sagas.

Implementations

Two-phase commit underlies the XA interface of the X/Open Distributed Transaction Processing model and the transaction managers of Java EE/Jakarta EE, as well as distributed transactions in many relational database systems.

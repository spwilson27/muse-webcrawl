Defensive programming

Defensive programming is a form of defensive design intended to develop programs that continue to function under unforeseen circumstances. Defensive programming practices are often used where high availability, safety, or security is needed: the programmer assumes that mistakes, invalid inputs, misuse of the software, and hostile actions will occur, and structures the code so that such problems are detected early and handled gracefully rather than causing unpredictable behaviour.

Practices

Common defensive programming techniques include:

  • Input validation — checking all data arriving from outside the program (users, files, networks, other processes) against explicit criteria before use, rejecting or sanitising invalid data.
  • Assertions — statements that check conditions the programmer believes must be true, so violations are caught during development and testing.
  • Checking return values and error codes — never assuming that operations such as file access, memory allocation, or network calls have succeeded.
  • Exception handling — structuring the program so that errors propagate to code that can respond meaningfully.
  • Design by contract — documenting and enforcing preconditions, postconditions, and invariants of functions.
  • Fail-safe defaults — for example, denying access by default, and using secure defaults in configuration.

Relation to secure programming

Defensive programming overlaps heavily with secure programming: many software vulnerabilities, such as buffer overflows and injection attacks, arise precisely where input was trusted without validation. The contrasting style is sometimes called "offensive programming", in which programmers let unexpected conditions fail loudly and immediately, on the theory that defensive checks can mask bugs and accumulate into "defensive" code that is itself complex and error-prone. In practice, safety- and security-critical code tends to combine both: validate all external inputs rigorously while asserting internal invariants.

Criticism

Critics argue that excessive defensive programming can reduce code clarity, hide defects that would be better fixed at the source, and introduce redundant checks that add maintenance burden and performance cost. The balance depends on the domain: pacemakers, avionics, and financial systems are usually written far more defensively than internal tools.

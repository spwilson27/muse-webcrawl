Test-driven development

Test-driven development (TDD) is a software development process relying on software requirements being converted to test cases before software is fully developed, and tracking all software development by repeatedly testing the software against all test cases. This is as opposed to software being developed first and test cases created later. The practice is closely associated with Kent Beck, who described it in Test-Driven Development: By Example (2003), and with the extreme programming (XP) methodology.

The cycle

TDD proceeds in a short repeating cycle often summarized as "red, green, refactor": (1) write a small automated test for a new behavior and run it — it should fail ("red"); (2) write the simplest production code that makes the test pass ("green"); (3) refactor both code and tests to improve design while keeping all tests passing. The cycle repeats for each increment of functionality, producing a comprehensive regression test suite as a byproduct.

Benefits and criticisms

Advocates argue TDD improves design by encouraging small, loosely coupled units, gives immediate feedback, reduces debugging time, and produces living documentation of intended behavior. Critics contend it can slow initial development, is difficult to apply to user interfaces, databases, and legacy code, and may give false confidence when tests are poorly written. Empirical studies show mixed but generally positive effects on external quality, with variable effects on productivity.

Related practices

Acceptance test-driven development (ATDD) and behavior-driven development (BDD) extend the idea to customer-facing acceptance criteria.

Distributed version control

A distributed version control system (DVCS, or distributed revision control) is a form of version control in which the complete codebase, including its full history, is mirrored on every developer's computer, in contrast to centralised version control, where only one copy of the history is held on a central server. Distributed revision control synchronises repositories by transferring patches from peer to peer, and there is no single central reference copy of the codebase by default; instead, there may be a copy designated as the official or blessed repository by convention.

Advantages and disadvantages

Because every clone contains the full history, most operations (committing, viewing history, reverting changes) are local and fast, and developers can work offline. Branching and merging are typically first-class operations, which encourages experimental work and parallel development. The model also provides inherent backup: any clone can restore the project if the main server is lost, and it offers strong integrity guarantees when combined with cryptographic hashing of content, as in Git.

Disadvantages include larger initial clones for projects with extensive history, difficulty handling very large binary files, and the absence of simple global revision numbers — distributed systems typically identify revisions by content hashes instead of sequential integers.

Systems

Examples of distributed version control systems include Git (created by Linus Torvalds in 2005 for Linux kernel development), Mercurial, GNU Bazaar (now Breezy), Darcs, Fossil, Pijul, and the earlier BitKeeper, GNU arch, and Monotone. Hosting services such as GitHub, GitLab, and Bitbucket provide centralised collaboration facilities on top of distributed systems, typically designating one repository as authoritative by social convention.

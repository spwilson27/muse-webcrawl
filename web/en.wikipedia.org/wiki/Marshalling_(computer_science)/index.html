Marshalling (computer science)

In computer science, marshalling or marshaling is the process of transforming the memory representation of an object into a data format suitable for storage or transmission, typically across a network or between different parts or languages of a program. It is similar to serialization and is used to communicate to remote objects with an object, for example parameters, messages, or return values. The inverse process is unmarshalling.

Usage

Marshalling is central to remote procedure calls (RPC), remote method invocation (such as Java RMI and .NET Remoting), and component technologies like COM and CORBA, where arguments to a call made in one address space (or apartment) must be packaged, possibly converted, and delivered to code running in another. In Microsoft's Component Object Model, "marshalling" specifically refers to the code — often generated proxy and stub objects — that transfers interface method calls and their parameters across apartment, process, or machine boundaries.

Marshalling also occurs in foreign function interfaces: when a managed runtime such as the .NET CLR calls native code, data types must be converted between representations (for example, a managed string to a null-terminated C string); .NET's Platform Invocation Services (P/Invoke) perform this via an interop marshaller that applies layout and conversion rules, which can be customised with attributes such as MarshalAs.

Comparison with serialization

The terms overlap, but a common distinction is one of intent: serialization encodes an object's state so it can be stored or recreated later, while marshalling is oriented toward passing parameters and results between remote or foreign execution contexts, and may include extra remote-specific information such as object references or code location. Marshalling also implies handling of references — a marshalled object graph can preserve remote references rather than copying every reachable object.

Security considerations

Unmarshalling untrusted data is a well-known attack surface: historical vulnerabilities in Java deserialization and in RPC marshaller implementations allowed remote code execution when crafted byte streams tricked the unmarshaller into constructing dangerous objects. Defensive practice recommends allow-lists of permitted types and avoiding native unmarshalling of untrusted input.

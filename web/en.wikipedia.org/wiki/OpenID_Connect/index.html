OpenID Connect

Developer: OpenID Foundation

Released: February 2014

Type: Identity layer / authentication protocol

Built on: OAuth 2.0

OpenID Connect (OIDC) is an authentication layer on top of the OAuth 2.0 authorization framework. It allows clients to verify the identity of an end user based on authentication performed by an authorization server, and to obtain basic profile information about the user in an interoperable, REST-like manner. OpenID Connect 1.0 is a finalized specification published by the OpenID Foundation in February 2014.

Overview

While OAuth 2.0 is designed for delegated authorization — granting applications access to resources — it does not itself define a standard way to authenticate users or represent their identity. OpenID Connect adds an identity layer: in addition to an OAuth access token, the authorization server returns an ID token, a JSON Web Token (JWT) containing claims about the authentication event and the user, such as the issuer (iss), subject identifier (sub), audience (aud), and expiration (exp).

Flows

The specification defines several flows. In the authorization code flow, the client receives a code after user authentication and exchanges it at the token endpoint for ID, access, and optionally refresh tokens; this is the recommended flow for most applications. The implicit flow returns tokens directly from the authorization endpoint and was designed for browser-based clients, though it is now discouraged. The hybrid flow combines elements of both.

Discovery and user information

OpenID Connect defines a Discovery mechanism by which clients retrieve provider metadata from a well-known URL (/.well-known/openid-configuration), including endpoints and signing keys, and a UserInfo endpoint that returns additional claims about the authenticated user. Standard claims include name, email, picture, and locale, requested via scopes such as openid, profile, and email.

Adoption

OpenID Connect is supported by major identity providers including Google, Microsoft (Entra ID), Okta, and many others, and underlies "Sign in with Google" and many enterprise single sign-on deployments. It succeeded the earlier OpenID 2.0 protocol, which was based on XML and a different extension model, and is distinct from it despite the similar name.

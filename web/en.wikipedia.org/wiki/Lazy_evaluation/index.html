In programming language theory, lazy evaluation, or call-by-need, is an evaluation strategy which delays the evaluation of an expression until its value is needed (non-strict evaluation) and which avoids repeated evaluations (by the use of sharing). Lazy evaluation is the default strategy in the functional programming language Haskell and can be opted into in many other languages through libraries or special constructs.

The opposite of lazy evaluation is eager evaluation, sometimes called strict evaluation, in which expressions are evaluated as soon as they are bound to variables. Lazy evaluation holds the potential for avoiding unnecessary work, enables infinite data structures such as lazy lists and streams, and can improve modularity by separating the generation of data from the control of its consumption.

History

Lazy evaluation was introduced independently by Peter Henderson and James H. Morris in 1971, and by Daniel P. Friedman and David S. Wise in 1974/76 in the context of cons cells and lambda calculus. Christopher Wadsworth had earlier proposed a related call-by-need semantics for the lambda calculus (1971). The strategy underlies Miranda, Lazy ML and Haskell.

Implementation

In an implementation that uses lazy evaluation, expressions are compiled into thunks — closures capturing the unevaluated expression and its environment. When a value is demanded, the thunk is forced; after evaluation, the thunk is overwritten with its result (memoised), so subsequent demands are free. Graph reduction is a classic implementation model. A known hazard is the "space leak", where long chains of unevaluated thunks accumulate instead of values.

Uses and drawbacks

Lazy evaluation makes it natural to define infinite lists (e.g., the Fibonacci sequence as a self-referential stream), supports demand-driven I/O and short-circuiting control structures as ordinary functions, and can avoid computing values that a program never uses. Drawbacks include unpredictable performance and memory behaviour, and difficulty reasoning about side effects and evaluation order, which is why most mainstream languages default to eager evaluation.

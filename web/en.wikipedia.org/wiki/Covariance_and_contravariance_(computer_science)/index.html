Covariance and contravariance (computer science)

In type theory, a type system is said to have variance if it describes how a type constructor's subtyping relationship changes depending on whether its type parameters are subtypes or supertypes of one another. A type constructor (such as a generic collection type or a function type) can be:

  • Covariant — if it preserves the ordering of types: if A is a subtype of B, then F<A> is a subtype of F<B>.
  • Contravariant — if it reverses the ordering: if A is a subtype of B, then F<B> is a subtype of F<A>.
  • Invariant — if neither relationship holds: F<A> and F<B> are unrelated unless A and B are the same type.
  • Bivariant — if both relationships hold, making the types interchangeable (rare and generally unsound or used for compatibility).

Examples

A read-only collection of Cat values can safely be treated as a read-only collection of Animal values, so a read-only list is covariant in its element type. Conversely, a "consumer" of Animal values (such as a function accepting an Animal) can be used where a consumer of Cat values is expected, because it can accept any animal, including cats; this makes function parameter types contravariant, while return types are covariant.

A mutable array or list is typically invariant: allowing a List<Cat> to be used as a List<Animal> would let a program insert a Dog into it, breaking type safety. Java famously made arrays covariant, which can produce a runtime ArrayStoreException and is now widely regarded as an unsound design choice mitigated by generics.

Language support

Languages such as C#, Scala, Kotlin and TypeScript support declaration-site variance annotations (out/in, +/-), while Java uses use-site variance through wildcards such as ? extends T (covariant) and ? super T (contravariant), guided by the mnemonic PECS: "producer extends, consumer super".

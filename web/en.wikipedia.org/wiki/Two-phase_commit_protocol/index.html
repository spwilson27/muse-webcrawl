Two-phase commit protocol

From Wikipedia, the free encyclopedia

The voting phase and the commit phase of 2PC

In transaction processing and distributed databases, the two-phase commit protocol (2PC) is a distributed algorithm that coordinates all the processes participating in a distributed atomic transaction, ensuring that either all of them commit or all of them abort — preserving atomicity even in the presence of failures.

How it works

The protocol involves one coordinator and several participants (cohorts). In the first phase, the commit-request (voting) phase, the coordinator asks each participant whether it is prepared to commit. Each participant writes the transaction's updates to a stable log and replies "yes" (vote commit) only if it can guarantee it will be able to commit later; otherwise it votes "abort", which unilaterally decides the outcome. In the second phase, the commit phase, if and only if every participant voted yes, the coordinator records the decision and instructs all participants to commit; otherwise all are told to roll back.

Properties and variants

2PC is a blocking protocol: if the coordinator fails after participants have voted yes but before announcing the decision, participants must wait (holding locks) until it recovers, because they cannot safely decide alone. Optimisations such as "presumed abort" and "presumed commit" reduce logging in common cases. The non-blocking three-phase commit adds an extra round to tolerate certain failures, at the cost of complexity and vulnerability to network partitions. Two-phase commit underlies the XA standard for distributed transactions across heterogeneous databases, though many modern large-scale systems instead favour looser consistency models.

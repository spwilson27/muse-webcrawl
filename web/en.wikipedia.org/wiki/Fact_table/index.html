Fact table

Fact table
ContextData warehousing, dimensional modeling
Key componentsMeasures, foreign keys to dimensions
Related conceptsDimension table, star schema, snowflake schema

In data warehousing, a fact table is the central table in a star schema or snowflake schema, surrounded by dimension tables. A fact table contains the quantitative data — the measurements, metrics, or "facts" — of a business process, together with foreign keys that link each row to the dimension tables describing the context of the measurement.

Structure

Each row in a fact table represents a single business event or measurement at a declared level of detail known as the grain of the table. A retail sales fact table, for example, might have one row per product sold on a receipt line, with measures such as quantity sold, unit price, discount amount and total sales amount. The primary key of a fact table is usually a composite of the foreign keys referencing its dimensions, sometimes supplemented by a degenerate dimension such as a transaction number.

Types of facts

Measures stored in fact tables are commonly classified as additive (can be summed across all dimensions, e.g. sales revenue), semi-additive (can be summed across some but not all dimensions, e.g. account balances over time), and non-additive (cannot be summed, e.g. ratios or percentages, which are typically derived from stored additive components).

Types of fact tables

Ralph Kimball's dimensional modeling methodology distinguishes several fact table types: transaction fact tables, which record one row per event; periodic snapshot fact tables, which summarise measures over regular time intervals; and accumulating snapshot fact tables, which track the progress of a process through defined milestones, updating rows as the process advances. Factless fact tables record events that have no numeric measures, such as student attendance, using only dimension keys.

Design considerations

Fact tables are typically the largest tables in a data warehouse, often containing billions of rows, and are usually kept narrow — few columns, many rows — to support fast aggregation. Surrogate keys are used for dimension references so that changes in source-system keys do not corrupt the warehouse history.

Database transaction

A database transaction symbolises a unit of work performed within a database management system against a database, treated in a coherent and reliable way independent of other transactions. A transaction generally represents a change in state of the database, and provides an all-or-nothing proposition: either every part of the transaction succeeds, or none of it does.

ACID properties

  • Atomicity — the transaction is indivisible; on failure, all its changes are rolled back.
  • Consistency — the transaction takes the database from one valid state to another, preserving all defined rules and constraints.
  • Isolation — concurrent transactions do not interfere with one another; the result is equivalent to some serial execution.
  • Durability — once committed, a transaction's effects survive system failures.

Control and isolation levels

In SQL a transaction begins implicitly or with BEGIN, and ends with COMMIT, making its changes permanent, or ROLLBACK, discarding them. Isolation levels — read uncommitted, read committed, repeatable read, and serializable — trade concurrency against anomalies such as dirty reads, non-repeatable reads, and phantom reads. Durability and atomicity are usually implemented with a write-ahead transaction log, while isolation is enforced by locking or multiversion concurrency control (MVCC).

Distributed transactions

When work spans multiple databases or services, protocols such as two-phase commit coordinate the participants, at the cost of availability during failures — the tension formalised by the CAP theorem and addressed in modern systems by patterns such as sagas and eventual consistency.

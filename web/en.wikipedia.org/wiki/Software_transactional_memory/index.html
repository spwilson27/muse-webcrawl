Software transactional memory

STM lets programmers mark blocks of code as atomic transactions instead of managing locks.

Software transactional memory (STM) is a concurrency control mechanism analogous to database transactions for controlling access to shared memory in concurrent computing. Instead of guarding shared data with locks, the programmer declares a block of code an atomic transaction; the runtime executes it speculatively and either commits its effects all at once, if no conflicting transaction interfered, or aborts and retries it. The concept was introduced in the early 1990s, notably in Maurice Herlihy's work on transactional memory (1993) and the software implementation by Nir Shavit and Dan Touitou (1995).

Motivation and semantics

Lock-based programming is error-prone: coarse-grained locks limit parallelism while fine-grained locks invite deadlock, race conditions, and poor composability — separately correct locked components often cannot be combined safely. Transactions promise composability: atomic blocks can be nested and combined, and the runtime handles conflicts. A transaction observes a consistent snapshot and either commits atomically or has no effect, providing the atomicity and isolation properties familiar from databases (though durability is not implied). Implementations differ in conflict detection (eager or lazy), versioning, and contention management, and must address problems such as irrevocable operations (a transaction cannot "unprint" output) and interaction with non-transactional code.

Implementations and adoption

STM is best known in Haskell, whose stm package (with the atomically and retry combinators, described by Tim Harris, Simon Marlow, Simon Peyton Jones and Herlihy in 2005) made it a standard feature influential in language design. Libraries exist for many languages (e.g., Clojure's built-in STM with refs, and experimental support in others). Intel and IBM also implemented hardware transactional memory in some processors, which can accelerate or complement software schemes. In practice, STM has seen selective rather than universal adoption, owing to performance overheads in some workloads, unresolved interactions with I/O, and the competing simplicity of message-passing and immutable-data styles of concurrency.

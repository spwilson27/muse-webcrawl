Interrupt handler

From Wikipedia, the free encyclopedia


Flow of control when an interrupt is serviced.

In computer science, an interrupt handler, also known as an interrupt service routine (ISR), is a special block of code associated with a specific interrupt condition. Interrupt handlers are initiated by hardware interrupts, software interrupt instructions, or software exceptions, and are used for implementing device drivers, real-time response to external events, multitasking, and other system services.

Operation

When an interrupt occurs, the processor suspends its current activity, saves enough state (such as the instruction pointer and status flags, and on some architectures the register set) to resume later, and transfers control to the handler identified through an interrupt vector table or descriptor table. The handler performs a small amount of time-critical work — acknowledging the device, moving data, or recording that an event happened — restores the saved state, and returns, allowing the interrupted program to continue as if nothing had happened.

Design constraints

Because handlers run asynchronously and may interrupt almost any code, they are heavily constrained: they must be short, cannot block or sleep, must be re-entrant or protected against nested interrupts, and can usually call only a restricted set of kernel services. Operating systems therefore split interrupt processing into a minimal "top half" (the hard-IRQ handler) and deferred work — softirqs, tasklets, workqueues, or threaded interrupts in Linux; deferred procedure calls in Windows — that runs later with fewer restrictions. This split keeps interrupt latency low while still allowing substantial processing.

Priorities and masking

Interrupt controllers such as the APIC assign priorities so urgent interrupts (timer, inter-processor) can preempt less urgent ones. Handlers can mask (disable) their own or lower-priority interrupt lines while running. Interrupt storms — a device repeatedly raising interrupts — can livelock a system, so drivers and kernels include mitigation and polling fallbacks (as in Linux's NAPI for network interfaces).

Software interrupts and exceptions

Not all handlers respond to hardware: processors provide instructions (such as INT on x86) that invoke handlers synchronously, historically used for system calls. Exceptions — faults, traps, and aborts arising from instruction execution, like page faults and divide-by-zero — are dispatched through the same mechanism, with handlers in the kernel deciding whether to satisfy the fault, deliver a signal, or terminate the process.

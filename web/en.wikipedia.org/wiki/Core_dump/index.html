Core dump

In computing, a core dump, memory dump, crash dump, storage dump, system dump, or ABEND dump consists of the recorded state of the working memory of a computer program at a specific time, generally when the program has crashed or otherwise terminated abnormally. In addition to the program's memory image, a core dump may include program state such as processor registers, call stack, management information, and other operating system or processor information.

Origin of the term

The name derives from magnetic-core memory, the dominant form of random-access computer memory from the 1950s to the 1970s: to "dump core" was to copy the contents of the core memory store out to paper or disk for analysis. The term has survived the technology, and the verb "to dump core" remains idiomatic for a program crashing in a way that produces such a snapshot; Unix systems traditionally write a file simply named core.

Use in debugging

A core dump allows a programmer to perform a post-mortem debugging session: loading the file into a debugger such as GDB together with the executable (and, ideally, symbol files) reveals where the program crashed, the values of variables, and the call stack at the moment of failure. Common triggers are fatal signals such as SIGSEGV (invalid memory reference), SIGABRT, and SIGBUS; a user can also force a dump with gcore or by sending SIGQUIT. On Linux, the size of core files is controlled by the ulimit -c resource limit, and modern distributions often pipe dumps to a handler such as systemd-coredump or Apport, which store them centrally and can generate crash reports. On Windows the equivalent artifacts are minidumps analyzed by Windows Error Reporting and WinDbg.

Contents and formats

On Unix-like systems, core dumps are usually written in the ELF format as an additional object type (ET_CORE), containing program headers describing the process's memory segments, register state (in notes sections), thread information, and the list of mapped files. Embedded systems may write dumps in simpler formats. Because dumps can be as large as the process's address space in use, administrators often restrict them; dumps may also contain sensitive data such as passwords or keys, so they are treated as security-sensitive artifacts.

History

Storage dumps were standard diagnostic practice on mainframes from the 1960s — IBM operating systems produced formatted dumps and ABEND (abnormal end) reports printed on fanfold paper — and the concept carried into Unix from its earliest versions, where the kernel wrote an image of a faulting process to the current directory.

Duck typing

Duck typing: if it walks like a duck and quacks like a duck, it can be treated as a duck.
Duck typing
ParadigmDynamic typing, structural typing
Common inPython, Ruby, JavaScript, Smalltalk
Named afterThe "duck test" attributed to James Whitcomb Riley

Duck typing is a style of dynamic typing in object-oriented programming in which an object's suitability for a particular purpose is determined by the presence of certain methods and properties, rather than by its actual type or class. The name comes from the duck test: "When I see a bird that walks like a duck and swims like a duck and quacks like a duck, I call that bird a duck."

Concept

In a duck-typed language, a function that expects an object with a quack() method will accept any object that has such a method, regardless of whether the object is declared to be a duck. This contrasts with nominative typing, where an object is usable only if it belongs to (or inherits from) a specific named type. Duck typing is closely related to structural typing, though structural type systems may check conformance at compile time.

Example

class Duck:
    def quack(self): return "Quack!"

class Person:
    def quack(self): return "I'm imitating a duck."

def make_it_quack(thing):
    print(thing.quack())

Both Duck and Person objects can be passed to make_it_quack, because both provide the required method.

Advantages and criticism

Duck typing encourages loose coupling and rapid prototyping, and underlies much of the flexibility of languages such as Python and Ruby. Critics note that errors surface only at runtime, and that implicit interfaces can be hard to discover; Python's "Easier to Ask Forgiveness than Permission" (EAFP) idiom, using try/except blocks, is a common companion practice. Later Python versions added protocols via the typing module to document and statically check duck-typed interfaces.

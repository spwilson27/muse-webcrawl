Remote procedure call

In distributed computing, a remote procedure call (RPC) is an inter-process communication (IPC) in which a computer program causes a procedure (subroutine) to execute in a different address space (commonly on another computer on a shared network), which is written as if it were a normal (local) procedure call, without the programmer explicitly coding the details for the remote interaction.

History

The idea dates to work by Bruce Jay Nelson at Xerox PARC in the late 1970s and early 1980s; his 1981 PhD thesis and the 1984 paper by Andrew Birrell and Nelson, "Implementing Remote Procedure Calls", set out the classic design of client stubs, marshalling, and a runtime that carries requests over the network. Sun Microsystems' RPC (later ONC RPC), documented in RFC 1057 and RFC 5531, became widely used with the Network File System (NFS).

Mechanism

An RPC system generates a client stub for each remote procedure. When the client calls the procedure, the stub packs (marshals) the arguments into a message, the runtime sends it to the server, and a server stub unpacks the arguments and calls the actual procedure. The return values travel back the same way. Interface definition languages (IDLs) are used to describe the procedures so that stubs can be generated for different programming languages and platforms; data is represented in a neutral format such as XDR, Protocol Buffers or JSON.

Systems and successors

Major RPC frameworks include ONC RPC, DCE/RPC (the basis of Microsoft RPC and COM/DCOM), CORBA, Java RMI, XML-RPC, SOAP, Thrift, and gRPC, which uses HTTP/2 and Protocol Buffers. RPC semantics raise issues not present in local calls: the call may fail after the server executes it, latency is orders of magnitude higher, and partial failures must be handled by the application, leading to the observation (popularised by Sun engineers) that distributed computing cannot simply be treated as local computing.

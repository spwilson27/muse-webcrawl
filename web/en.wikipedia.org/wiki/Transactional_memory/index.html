Transactional memory

Transactional memory is a concurrency control mechanism in concurrent computing that simplifies parallel programming by allowing a group of load and store operations to execute in an atomic way. It is a concurrency control mechanism analogous to database transactions for controlling access to shared memory in concurrent computing. Transactional memory systems provide high-level abstraction as an alternative to low-level thread synchronization constructs such as locks.

Motivation

Writing correct and efficient concurrent programs with locks is difficult: coarse-grained locking serializes execution, while fine-grained locking is error-prone and can lead to deadlock and other hazards. Transactional memory lets programmers declare a block of code as atomic; the underlying system executes it speculatively, tracking the memory locations read and written. If two concurrent transactions conflict, one is aborted and re-executed, guaranteeing that committed transactions appear to have executed serially (serializability) and without intermediate states visible to others.

Hardware transactional memory

Hardware transactional memory (HTM) implements transactions using cache coherence machinery and speculative buffering in the processor. Commercial implementations include IBM's Blue Gene/Q and POWER8 processors, and Intel's Transactional Synchronization Extensions (TSX), introduced with the Haswell microarchitecture, which provide instructions such as XBEGIN, XEND and XABORT. HTM is fast but typically best-effort: transactions may abort for capacity or implementation reasons, requiring a software fallback path.

Software transactional memory

Software transactional memory (STM) implements the mechanism in a library or language runtime, commonly using versioning, ownership records, or word-based locks, and conflict detection at commit time. STM is available in languages such as Haskell (where it is part of the standard platform), Clojure, and through libraries for C, C++, Java and Scala.

Comparison with locking

Transactions offer composability — atomic blocks can be nested and combined without knowledge of their contents — and avoid many deadlock scenarios. However, they face difficulties with irrevocable operations such as I/O, interactions with non-transactional code, and worst-case performance under high contention.

History

The idea originated in a 1993 paper by Maurice Herlihy and J. Eliot B. Moss, who proposed transactional memory as an extension of cache coherence protocols. Software transactional memory grew through research systems in the 1990s and 2000s, and hardware support reached commercial processors in the early 2010s.

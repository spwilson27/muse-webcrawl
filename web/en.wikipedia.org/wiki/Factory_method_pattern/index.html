Factory method pattern

In class-based programming, the factory method pattern is a creational pattern that uses factory methods to deal with the problem of creating objects without having to specify the exact class of the object that will be created. This is done by creating objects by calling a factory method — either specified in an interface and implemented by child classes, or implemented in a base class and optionally overridden by derived classes — rather than by calling a constructor directly.

Overview

The pattern was popularized by the 1994 book Design Patterns: Elements of Reusable Object-Oriented Software by the "Gang of Four" (Gamma, Helm, Johnson, and Vlissides), where it appears as one of the five creational patterns. It is distinct from the simpler "simple factory" idiom (a single static method that chooses a concrete class) and from the abstract factory pattern, which creates families of related objects.

Structure

  • Product — the interface (or abstract class) of objects the factory method creates.
  • Concrete Product — implementations of the Product interface.
  • Creator — declares the factory method, which returns a Product; the Creator may also define a default implementation and uses the factory method within its own operations.
  • Concrete Creator — overrides the factory method to return a particular Concrete Product.

Example

A classic example is a document-processing framework: an Application class declares a factory method createDocument(); subclasses such as a word processor or spreadsheet application override it to instantiate their own document types, while shared framework code works with the abstract document interface. GUI toolkits use the same idea to create platform-specific widgets from abstract factories and factory methods.

// Pseudocode
abstract class Dialog {
    abstract Button createButton();  // factory method
    void render() { Button b = createButton(); b.show(); }
}
class WindowsDialog extends Dialog {
    Button createButton() { return new WindowsButton(); }
}
class WebDialog extends Dialog {
    Button createButton() { return new HTMLButton(); }
}

Advantages and disadvantages

The pattern decouples client code from concrete classes, follows the open/closed principle (new product types are added by adding subclasses), and gives a single point of control over instantiation. Its costs include an explosion of subclasses — one creator per product — and added indirection that can complicate simple programs. In modern practice, dependency-injection frameworks and language features such as first-class functions often cover the same needs, but the factory method remains fundamental in frameworks and libraries.

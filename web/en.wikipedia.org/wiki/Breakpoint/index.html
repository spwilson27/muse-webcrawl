Breakpoint

In software development, a breakpoint is an intentional stopping or pausing place in a program, put in place for debugging purposes. When execution reaches a breakpoint, the program halts and control passes to the programmer, who can inspect variables, memory, and the call stack, and then resume execution, step through subsequent instructions, or terminate the run. Breakpoints are the central feature of a debugger and are used far more commonly than older techniques of stopping programs with inserted print statements or manual halts.

Red dots in the gutter of an IDE mark breakpoints in source code

Types

  • Line breakpoints pause execution when a specified line of code (or machine address) is reached.
  • Conditional breakpoints pause only when a given expression evaluates to true, sparing the programmer from stepping through many irrelevant iterations of a loop.
  • Watchpoints (data breakpoints) pause when a variable or memory location is read or written, helping to find where a value is corrupted.
  • Exception breakpoints pause when the program throws or is about to throw an exception.
  • Function breakpoints pause on entry to a named function, regardless of where it is called from.
  • Logpoints print a message to the debug console when reached without pausing execution.

Implementation

Early debuggers implemented breakpoints by inserting a special instruction into the program. On x86 processors the canonical mechanism is the INT 3 instruction (opcode 0xCC), a single byte that replaces the first byte of the target instruction; when executed it raises a breakpoint exception caught by the debugger, which restores the original byte and presents the stopped program. Because instruction replacement is impractical in read-only memory or when many watchpoints are needed, processors also provide hardware breakpoint registers (such as the x86 debug registers DR0–DR3) that compare addresses without modifying code. Software breakpoints are effectively unlimited in number; hardware breakpoints are few but can monitor data accesses as well as execution.

History

The concept dates to the earliest days of computing: operators of machines such as ENIAC and the early stored-program computers could set switches to halt execution at a chosen instruction and inspect the machine's state. The term and the debugger-based workflow became standard with interactive computing and integrated development environments from the 1970s onward, popularised by tools such as Unix's dbx, Microsoft's CodeView, and modern debugger front ends built on GDB and LLDB.

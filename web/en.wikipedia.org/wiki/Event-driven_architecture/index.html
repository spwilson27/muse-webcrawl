Event-driven architecture

Event-driven architecture (EDA) is a software architecture pattern promoting the production, detection, consumption of, and reaction to events. An event is a significant change in state — for example, "an order was placed", "a payment was received" or "a sensor reading exceeded a threshold". In an event-driven system, components communicate by emitting and receiving event notifications rather than by making direct requests of one another, which produces loosely coupled systems that are easier to extend and scale.

Concepts

The basic building blocks of EDA are:

  • Event producers (or emitters) — sources that detect or cause state changes and publish events describing them.
  • Event consumers — components that subscribe to events and react when they receive them, by updating data, triggering workflows, or emitting further events.
  • Event channels and brokers — middleware, such as message brokers and streaming platforms, that route events from producers to consumers (e.g. Apache Kafka, RabbitMQ, Amazon EventBridge).
  • Events — immutable records of facts, typically carrying a timestamp, a type, and a payload describing what happened.

Styles of event processing

Simple event processing reacts to individual events as they occur. Event stream processing analyses flows of events, often with continuous queries. Complex event processing (CEP) detects patterns and correlations across multiple events — for example, inferring a fraud attempt from a sequence of transactions. EDA is closely related to, but distinct from, the publish–subscribe pattern, message-driven architecture, and reactive programming.

Advantages and challenges

Advantages of EDA include loose coupling (producers need not know who consumes their events), scalability (consumers can be added and scaled independently), responsiveness to real-time data, and extensibility — new behaviour can often be added by subscribing a new consumer without modifying existing components. Challenges include the difficulty of tracing and debugging asynchronous flows, ensuring ordering and exactly-once delivery, handling failures and duplicate events, schema evolution, and a loss of the simple mental model of synchronous request–response interactions.

Applications

Event-driven designs are widely used in microservices architectures, e-commerce order processing, financial trading and fraud detection, Internet of Things systems, user interfaces (which are inherently event-driven), and data pipelines. Related patterns include event sourcing, in which state is derived from a log of events, and CQRS (command query responsibility segregation).

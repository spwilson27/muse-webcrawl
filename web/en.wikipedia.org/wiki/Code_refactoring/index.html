Code refactoring

Refactoring restructures code without changing its behaviour

Discipline: Software engineering

Key text: Martin Fowler, Refactoring (1999; 2nd ed. 2018)

Code refactoring is the process of restructuring existing computer code — changing its internal factoring — without changing its external behaviour. The term originates in mathematics (factoring an expression) and was popularised in software engineering by Martin Fowler's 1999 book Refactoring: Improving the Design of Existing Code, which catalogued named refactorings such as Extract Method, Rename Variable and Move Method. Typical goals include improving readability, reducing complexity and duplication, removing code smells, and making the software easier to extend and maintain.

Motivations

Software tends to lose its original design coherence as features are added under time pressure ("software rot" or technical debt). Refactoring counteracts this by continually improving the design in small, behaviour-preserving steps. It is a core practice of extreme programming (XP) and test-driven development, in which the "red–green–refactor" cycle makes refactoring the third step after making a failing test pass.

Techniques and safety

Common refactorings include extracting duplicated code into functions, renaming identifiers for clarity, replacing conditionals with polymorphism, introducing parameter objects, and breaking large classes or functions into smaller units. Because refactoring by definition does not change behaviour, a comprehensive automated test suite is the principal safety net, and modern integrated development environments automate many mechanical transformations with guaranteed correctness. Refactoring is distinct from rewriting (replacing a system wholesale) and from bug fixing or adding features, although in practice small refactorings are often interleaved with other work.

Challenges

Large-scale refactorings in legacy systems without tests carry risk, and managers may resist time spent on work that produces no visible features. Practitioners argue that regular small refactoring is cheaper than deferred "big bang" cleanup, which is frequently abandoned or introduces regressions.

Shared library

Several programs using one shared library in memory

A shared library or shared object is a file intended to be shared by executable files and other shared object files. Modules used by a program are loaded from individual shared libraries into memory at load time or runtime, rather than being copied into a single monolithic executable file. Shared libraries can be statically linked during program composition into an executable (in which case they behave much like plain object files) but are more commonly loaded dynamically, so that a single copy of the library code can serve many programs at once and can be updated without recompiling the programs that use it.

Benefits

  • Memory savings: the library's code pages are mapped into many processes at once, so the physical memory cost is paid roughly once.
  • Disk savings: executables contain references to the library rather than copies of it.
  • Maintainability: security fixes and improvements to a library propagate to all programs using it when the shared library is upgraded.
  • Modularity: libraries provide a natural plugin and extension mechanism.

Risks and drawbacks

Sharing introduces dependency risks: an incompatible update to a shared library can break applications that rely on it — a problem colloquially known as "DLL hell" on Windows. Versioning schemes, symbol versioning, and side-by-side installation of multiple versions attempt to mitigate it. Dynamic loading also carries a small runtime cost and, historically, complicated the security model through search-path hijacking attacks when library lookup paths are not controlled.

Implementation by platform

Unix and Linux

On Unix-like systems, shared libraries are ELF files with the suffix .so (shared object), conventionally named libname.so.version with a SONAME recorded inside the file. The dynamic linker/loader (ld.so) resolves symbols at program startup, searching directories in /etc/ld.so.cache, the LD_LIBRARY_PATH environment variable, and built-in default paths; tools such as ldd list a binary's library dependencies. Position-independent code (PIC) allows the same library pages to be shared even when mapped at different addresses in each process.

Windows

On Microsoft Windows, shared libraries are dynamic-link libraries (DLLs) with the .dll extension. Windows searches the application's directory, system directories, and the PATH; modern versions support side-by-side assemblies and private (application-local) copies to avoid version conflicts.

macOS

macOS uses dynamically linked libraries with the .dylib extension and frameworks bundling libraries with their resources, resolved by the dynamic linker dyld.

History

Shared libraries became mainstream with Multics and later Unix System V and SunOS in the 1980s, which introduced the modern .so model, and with Windows 3.x and OS/2, which popularised DLLs. They contrast with static libraries (.a, .lib), whose code is copied into the executable at link time, and with the practice of shipping fully self-contained (" vendored") binaries.

Reflective programming

Reflection lets a program examine and modify its own structure and behaviour at runtime.

In computer science, reflective programming or reflection is the ability of a process to examine, introspect, and modify its own structure and behaviour. Programs written in languages supporting reflection can treat code as data: they can enumerate the methods and fields of a class, construct objects from a class name supplied at runtime, invoke methods by name, and sometimes generate new code dynamically. Reflection is a cornerstone of metaprogramming.

Types

Introspection is the ability of a program to observe its own structure — for example, asking an object for its class or listing an object's methods. Intercession goes further, letting the program alter that structure, such as adding methods or changing behaviour at runtime. Languages differ widely in how much reflection they permit: Smalltalk and Lisp expose nearly everything, Java and C# provide rich reflection APIs over class metadata, Python exposes objects' attributes through functions such as getattr and modules such as inspect, while C++ offers only limited runtime type information, supplemented by compile-time template metaprogramming.

Uses

Reflection powers frameworks that must work with user code generically: object-relational mappers that map database tables to classes, dependency-injection containers, serialisation libraries, unit-testing frameworks that discover test methods by naming conventions, remote-procedure-call systems, and plug-in architectures that load classes named in configuration files. It is also used in debugging and development tools, mock objects, and aspect-oriented programming.

Trade-offs

Reflection generally costs performance — reflective calls bypass static type checking and many optimisations — and can undermine encapsulation and security, since private members can be accessed or altered where the runtime permits it. Reflective code can also be harder to analyse, refactor and verify than statically resolved code, so most style guidance recommends using it sparingly and mainly in framework code.

Database transaction

A transaction either commits in full or rolls back entirely

A database transaction symbolises a unit of work, performed within a database management system against a database, that is treated in a coherent and reliable way independent of other transactions. A transaction generally represents any change in a database, and in a database system has the purpose of maintaining the system's integrity in a known, consistent state.

ACID properties

Transactions in relational databases are traditionally described by the ACID properties: atomicity (all operations in the transaction succeed, or none do), consistency (the database moves from one valid state to another), isolation (concurrent transactions do not interfere), and durability (once committed, the result survives crashes). Database systems implement these using write-ahead logging, locking or multiversion concurrency control (MVCC).

Transaction control

In SQL, a transaction begins implicitly or with BEGIN, is made permanent with COMMIT, and is undone with ROLLBACK; savepoints allow partial rollback. Isolation levels — read uncommitted, read committed, repeatable read and serializable — trade strictness against concurrency and guard against anomalies such as dirty reads, non-repeatable reads and phantoms.

Distributed transactions

When work spans several databases or services, protocols such as two-phase commit coordinate the participants, at the cost of availability; many large-scale systems instead adopt eventual consistency or compensating "saga" patterns.

Shard (database architecture)

A shard is a horizontal partition of data in a database or search engine. Each shard is held on a separate database server instance, distributing the load; together the shards form a single logical database. Sharding is thus a method of horizontal scaling, in contrast to vertical scaling (increasing the capacity of a single server).

Architecture

In a sharded system, rows of a table are distributed across servers according to a shard key — for example, customer ID ranges (range sharding) or a hash of the key (hash sharding). Each shard holds the same schema but a disjoint subset of the data, typically replicated for availability. Queries that include the shard key can be routed to a single shard, while cross-shard queries require the application or middleware to scatter and gather results.

Advantages and drawbacks

Sharding reduces the data per server, improves write throughput, and limits the blast radius of failures. However, it complicates joins across shards, rebalancing when shards become uneven, maintaining unique constraints, and operational management. Many distributed SQL and NoSQL systems — such as MongoDB, Cassandra, Vitess, and Google's Spanner — automate parts of sharding.

Etymology

The term is often said to derive from "SHARD" (System for Highly Available Replicated Data), a 1980s research project, though it also evokes the image of a database broken into shards like fragments of pottery.

Memory safety

Memory safety
Domain: computer security, programming languages
Prevented flaws: buffer overflow, use-after-free, null dereference, data races
Approaches: garbage collection, borrow checking, bounds checking

Memory safety is the state of being protected from various software bugs and security vulnerabilities when dealing with accesses to memory, such as buffer overflows and dangling pointers. A programming language is said to be memory-safe if its programs cannot access memory outside the bounds intended, read uninitialized memory, or use memory after it has been freed. Studies by Microsoft and the Chromium project have attributed roughly 70 percent of serious vulnerabilities in large C and C++ codebases to memory-safety defects.

Categories of errors

Spatial errors violate bounds: buffer overflows and over-reads (as in the Heartbleed bug) access memory beyond an allocated object. Temporal errors violate lifetime: use-after-free, double free, and dangling pointers reference memory that is no longer valid. Other memory errors include null-pointer dereferences, uninitialized reads, memory leaks, and—in concurrent programs—data races. Exploits built on such errors can yield arbitrary code execution, which is why memory safety is central to operating system and browser security.

Approaches

Languages such as Java, C#, Python, and Go achieve memory safety through managed runtimes with garbage collection and runtime bounds checks, at some cost in latency and control. Languages like Lisp pioneered these techniques. Rust achieves memory safety without garbage collection through its ownership and borrow-checking system enforced at compile time, making it attractive for systems programming; it has been adopted in the Linux kernel and in components of Windows and Android. Other strategies include static analysis and formal verification, sanitizers and fuzzing in C/C++, hardware features (such as ARM memory tagging and capability architectures like CHERI), and rewriting critical components in safe languages. In 2023–2024, United States government agencies including the NSA and CISA published guidance urging roadmaps away from memory-unsafe languages in new products.

Trade-offs

Memory-safe languages historically imposed performance overhead or garbage-collection pauses, driving continued use of C and C++ in kernels and embedded systems. Modern designs—with escape analysis, reference counting, or Rust-style ownership—have narrowed the gap, while unsafe escape hatches in otherwise safe languages confine risk to audited code sections.

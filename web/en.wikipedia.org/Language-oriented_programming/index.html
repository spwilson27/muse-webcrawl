Language-oriented programming

Language-oriented programming (LOP) is a software development paradigm that centers on creating and using domain-specific languages (DSLs) tailored to particular problem domains, rather than forcing solutions into a general-purpose language. In this style of development, the programmer builds a small language whose constructs mirror the concepts of the application domain, and then expresses the bulk of the solution in that language.

Overview

The term was popularized in the 1990s, notably in a 1994 paper by Martin Ward, "Language Oriented Programming". The approach has older roots in Lisp culture, where macros allow programmers to extend the language toward the problem, and in the Unix philosophy of little languages such as awk, sed, and configuration notations.

Language-oriented programming treats the design of notation itself as a central engineering activity. Instead of a single monolithic general-purpose language, a project may employ a family of small languages — one for describing data layouts, one for business rules, one for build configurations — each designed so that domain experts can read, and sometimes write, programs in them.

Language workbenches

A language workbench is an integrated development environment designed to support LOP by making it cheap to define new languages along with their editors, debuggers, and code generators. Examples include JetBrains MPS, which uses a projectional editor so languages can be freely composed, the Spoofax language workbench, and Xtext. Lisp-family languages such as Racket were explicitly designed to support the creation of embedded and standalone DSLs, leading to the slogan of "languages as libraries".

Advantages and criticisms

Advocates argue that well-designed domain languages raise the level of abstraction, reduce boilerplate, make code closer to the requirements, and allow domain experts to participate directly in development. Critics note that designing a good language is difficult, that proliferating DSLs fragment tooling and increase the learning burden for new team members, and that a poorly designed DSL can be harder to escape than a general-purpose language.

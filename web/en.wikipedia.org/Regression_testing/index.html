Regression testing

Regression testing (rarely, non-regression testing) is re-running functional and non-functional tests to ensure that previously developed and tested software still performs after a change. The changes that may require regression testing include bug fixes, software enhancements, configuration changes, and the substitution of electronic components. If test changes are not made, the problems that can emerge include software regressions, in which previously working functionality stops working.

Background

As software is modified — features added, defects repaired, code refactored — new defects may be introduced or old ones uncovered in parts of the system that were not changed directly. Regression testing aims to detect such unintended side effects. The term is also used for the general class of tests that verify an identified bug has been fixed and has not returned.

Techniques

A regression test suite grows over the life of a project and quickly becomes too expensive to run in full after every change. Common strategies include:

  • Test case prioritization — ordering tests so those most likely to detect faults run first.
  • Test suite reduction — removing redundant or obsolete tests.
  • Selective retesting — running only tests affected by the changed code, guided by dependency or coverage analysis.
  • Automation — regression suites are a prime target for automated testing, since they are executed repeatedly; in agile practice they commonly run in continuous integration pipelines.

Sanity and smoke testing

Regression testing differs from sanity testing and smoke testing, which are quick, shallow checks that a build is stable enough for further testing. Regression testing is deeper: it re-verifies a broad range of existing behaviour. It is typically performed at system and acceptance level, and at unit level through automated unit test suites.
